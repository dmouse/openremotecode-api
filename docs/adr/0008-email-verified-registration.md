# ADR 0008: Email-Verified Registration

## Status

Accepted. Supersedes ADR 0001's decision that "local registration currently creates active, unverified users because email delivery is not implemented. The route is disabled unless the process explicitly enables development registration under `APP_ENV=development`." Registration is now verified by email and enabled by default in every environment.

## Context

Registration existed but could not be used in production. `Register` marked a new account `active` immediately and logged the caller straight in, with nothing proving the registrant controlled the address they claimed. ADR 0001 named this as the reason the route sat behind `ENABLE_INSECURE_DEVELOPMENT_REGISTRATION`, and the schema already carried unused `pending` and `active` states and an unused `email_verified_at` column in anticipation of the fix.

Without verification, anyone could take any address, including one belonging to someone else, and an address could not be relied on for any future purpose such as recovery or security notices. ADR 0006 separately recorded that the mobile app had no registration UI.

The threats specific to this phase are account enumeration through the registration response, verification-code guessing, mail-based amplification (using registration or resend to send unsolicited mail), a pending account obtaining authorization it should not have, and a mail host hanging a request.

## Decision

**An account cannot pair a device, obtain relay admission, or reach any authenticated route until its email address is verified.** This is a product rule in its own right, not merely a consequence of the session model.

- Accounts are created `pending`. `VerifyEmail` is the only path that promotes an account to `active`, and it sets `email_verified_at` at the same time.
- Verification is a six-digit code entered in the app, not a link. There is no web client for a link to land on (ADR 0006). Codes are generated from `crypto/rand` by rejection sampling so that every value is equally likely, live for ten minutes, and allow eight wrong attempts before a new one must be requested.
- **Verification is ticket-scoped, not session-scoped.** `Register`, and `Login` against a still-pending account, return an unauthenticated verification ticket (an opaque `vft_` value using the same issue/hash machinery as refresh credentials) scoped to `POST /v1/auth/verify-email` and `POST /v1/auth/resend-verification`. Those two endpoints look the ticket up directly and never consult `AuthenticateAccess`, `AuthorizeAccount`, or `AuthorizeSession`. PostgreSQL stores only the SHA-256 hashes of the ticket and the code.
- A pending account is therefore excluded from pairing and relay **by construction**, with no new checks in those modules: `AccessPrincipalByAccessTokenHash`, `ActiveAccountByID`, and `ActiveSessionByID` each already filter `status = 'active'` in SQL, so no session minted for a pending account would authenticate anywhere. Minting one would have been misleading rather than useful.
- `Login` against a pending account returns a verification challenge rather than `ErrInvalidCredentials`. This is safe because the caller has already proved the password, so it discloses only what they just demonstrated. Within the thirty-second resend cooldown the outstanding code is reused and only the ticket rotates, so repeated sign-in attempts do not send repeated mail; a reused code keeps its attempt count, because the cap belongs to the code. Every other account status still collapses into the generic `ErrInvalidCredentials`.
- **Registration answers an already-registered address with a decoy challenge.** `ErrEmailUnavailable` and the `409 account_unavailable` response are removed outright rather than left reachable. The conflict is still detected as a `CreateUser` conflict rather than a pre-flight lookup, which avoids both a TOCTOU race and a timing difference; the password hash runs before the transaction on both paths. On conflict the service rolls back, mails the address a notice that someone attempted to register it, and returns a well-formed `vft_` ticket backed by no database row, with the same status code, the same response shape, and a synthetic account that reports nothing about the real one. A code submitted against it fails as an ordinary invalid code. The attempt is audited as `auth.registration_conflict` with no user ID, so the audit trail does not answer the question the response refuses to.
- **Mail is sent after the transaction commits, never inside it.** Registration returns `201` with a usable challenge regardless of the delivery outcome. This keeps a network round trip out of the database transaction, removes the rollback and failure-ordering paths entirely, and means the user row exists by the time a delivery failure needs recording. The account left behind by a failed send is an ordinary pending account, recoverable through resend or by signing in again.
- Mail goes out over SMTP configured by environment variables, using stdlib `net/smtp` with no third-party dependency. `SMTP_TLS_MODE` defaults to `starttls` on port 587 for the broadest provider compatibility, with `tls` available for providers requiring implicit TLS. Production requires `SMTP_HOST` and `SMTP_FROM_ADDRESS` and rejects `none`, failing closed in the same style as `PAIRING_CODE_KEY`. **The mailer enforces its own ten-second deadline** on both the dial and the session, because `net/smtp` sets none and an unresponsive host would otherwise hang the request indefinitely.
- In development only, an empty `SMTP_HOST` selects a mailer that logs the code instead of sending it. This is the single deliberate exception to "never log credentials": in development the log *is* the delivery channel. The configuration loader rejects this arrangement outside development.
- `REGISTRATION_ENABLED` replaces `ENABLE_INSECURE_DEVELOPMENT_REGISTRATION`, defaults to **true**, and sits outside the fail-closed "insecure development features require `APP_ENV=development`" check. It is an operational kill switch, not a security control: registration is no longer a downgrade now that an account is unusable until verified. A malformed value still fails startup rather than silently disabling the route.
- New per-address rate limits layer on top of the per-challenge limits: ten verification attempts per ten minutes and three resends per ten minutes, sized like the existing register (5/10min) and login (10/min) limits.
- `email_bounced_at` on `users` records when delivery to an address last failed permanently. It is a nullable timestamp rather than a boolean so it records *when*, matching `email_verified_at`. It lives on the account rather than on the verification row because deliverability is a property of the address and must outlive a row that is deleted on success.

### What the bounce field can and cannot know

`net/smtp` surfaces only *synchronous* failures: a 5xx at `RCPT TO` or `DATA` while the connection is open. A message the relay accepts and bounces later produces a DSN to the envelope sender or a provider webhook, neither of which this client sees. So `email_bounced_at` means "delivery failed at handoff" today.

The mailer distinguishes two failure classes because they receive different treatment. `ErrMailUndeliverable` is a permanent per-recipient 5xx rejection and records a bounce. `ErrMailDeliveryFailed` is transient — timeout, connection refused, 4xx, authentication failure, or a rejected *sender*, which is our own misconfiguration — and **must not** record one, or an outage would mark every user's address bad. A successful send clears a stale flag, so a mailbox that starts working again stops looking broken.

**A bounce never blocks anything.** It is diagnostic state only: resending stays available, and no authorization path may consult it. Only `status` gates access. Registration's decoy path is the one asymmetry — a notice to an existing address that hard-bounces flags that existing user — but the response stays the identical decoy challenge, because the flag must never become an enumeration side channel.

### Deferred: asynchronous bounce ingestion

Not built. The column and its setter are the entire integration surface: a webhook handler would resolve the payload's recipient through the existing `Repository.UserByNormalizedEmail` and call the same `SetEmailBounced`, with no schema change, no new store method, and no change to any reader. Correlation is deliberately by address rather than by send — the question the field answers is "is this address deliverable," which the address alone answers — so no `Message-ID` is emitted or stored. When it is built: its own route outside the `/v1/auth` group (that group's origin and Fetch Metadata gate is a browser CSRF control and the wrong one for a server-to-server POST), authenticated by provider HMAC signature compared with `crypto/subtle` plus a timestamp tolerance for replay, behind the existing body cap and a rate limiter, treating the payload as wholly untrusted. The "never gates access" rule above is what keeps accepting such input safe: once an external party can write bounce state, a forged or replayed payload must be able to cause diagnostic noise and nothing worse.

## Consequences

- **Existing accounts are untouched.** Every current row is `active` with `email_verified_at` NULL, and they keep working with no forced re-verification. `ActivateUser`'s pending-only `WHERE` clause guarantees this change cannot move them. Nothing anywhere, server or mobile, may gate access on `emailVerified == true` — doing so would lock out every existing user. Only `status` is authoritative for access, and `emailBounced` is likewise never a gate.
- **The wire change is backward compatible in practice.** Active-account login keeps its exact response shape, and no pending accounts exist today, so an already-installed app is unaffected. As belt and braces, the mobile `AuthSession.parse` already rejects a non-active account with 403.
- **Registration no longer reports a taken address.** A client cannot distinguish a new registration from a duplicate, by design. The mobile verification screen is therefore also where someone who forgot they had an account lands, so its copy states that a code was sent *if* the address is not already registered and offers a route to sign in. This is the cost of closing the enumeration oracle, and it is accepted.
- **Registration commits before it sends.** A mail failure leaves a pending account rather than failing registration; the user recovers via resend or by signing in again, and the bounce flag records why. Chosen over rolling back to keep the path simple and to avoid holding a transaction across a network round trip.
- **Expired `email_verifications` rows are never swept.** They are bounded by the pending-account count, replaced in place on reissue, and cascade-deleted with the user, so there is no unbounded growth. A sweeper is deliberately deferred.
- A verification code is mailed in plaintext, so it is only as confidential as the user's mailbox. That is inherent to email verification; the ten-minute lifetime, eight-attempt cap, and single-use consumption bound the exposure.
- The server now has an outbound network dependency on a mail host. Readiness deliberately does not include it: mail is not required to serve existing accounts, and ADR-level guidance is that readiness should not depend on optional third-party services. A mail outage blocks new registrations from completing but leaves every existing account working.

## Verification

`go test ./...` with `-race`, including: registration producing a pending challenge and mailing a code; a duplicate address producing a response indistinguishable from a fresh one, creating no account, mailing a notice instead, and rejecting a code submitted against the decoy ticket; a wrong code incrementing attempts **durably**, since the increment is committed by returning nil from the transaction closure and would be silently rolled back if that ever became an error return; expired and attempt-exhausted challenges rejected; sign-in against a pending account reusing the code within the cooldown and rotating it past the cooldown; resend cooldown enforced and a non-pending account answered like an unknown ticket; an existing `active` account with a NULL `email_verified_at` still signing in; bounce recorded only for permanent failures, cleared by a later success, and never blocking login, resend, or verification; and the mailer surfacing a transient failure within its deadline against a host that never answers.

Integration tests additionally cover the `email_verifications` cascade delete, ticket-hash uniqueness, and `FOR UPDATE` serialization of a concurrent verify and resend. A cross-module test enumerates every connector route from `RegisterRoutes` and asserts that a pending account holding an otherwise-valid session and access token is rejected with 401 on each account-authenticated one, with the same fixture flipped to `active` admitted — so a newly added route that skips the check fails as unclassified rather than passing untested.

Manually: `docker compose up`, register, read the code from the server log, verify, and confirm that login then returns a session; confirm a wrong code increments attempts and eventually locks the challenge out; confirm resend rotates the code and respects the cooldown.
